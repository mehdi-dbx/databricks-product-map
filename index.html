Chapter 1

Data Storage & Movement

Every model and agent reads data, and that data has to be stored somewhere first.

This layer decides where the data lives and in what format, and open formats in the organization's own storage keep every engine able to read it.

Everything built later reads from here.

  • Table Formats
  • Ingestion & Pipelines
  • Transactional & Real-Time Data
  • Table Maintenance
Data Storage & Movement

1.1 Table Formats

Keep one consistent copy of your data, in an open format.

The first decision is how the data is stored, because every engine, model and agent downstream inherits it.

Challenges
  • Batch and streaming data often sit in separate stores, sometimes in closed or complex formats.
  • A job that fails halfway can leave a table inconsistent.
  • A schema change can break the jobs that read it.

Delta Lake is the default table format.

  • The tables live in your own cloud storage.
  • Delta adds transactions to those files.
  • Batch jobs and streaming jobs write to the same tables without corrupting them.
  • The schema can change without breaking readers.
  • Tables can also use Apache Iceberg, the other open table format.
  • Multi-table transactions commit changes to several tables at once.

1.2 Ingestion & Pipelines

Source data lands in the tables with no pipeline code to write or run.

Open tables are only useful once the data from the source systems reaches them.

Challenges
  • Getting it there means writing connector code for each source and wiring job dependencies by hand.

Lakeflow covers ingestion and transformation.

  • Lakeflow Connect provides managed connectors to databases and SaaS applications, query-based and community connectors, and Auto Loader for files.
  • Zerobus Ingest brings in event data.
  • Spark Declarative Pipelines describe the transformations, and Lakeflow works out the order in which to run them.
  • They are written in the Lakeflow Pipelines Editor, or on a visual canvas in Lakeflow Designer, and can run in real-time mode.
  • Lakeflow Jobs orchestrates the workflows.

1.3 Transactional & Real-Time Data

Applications and agents keep their data on the same platform as the analytics, under the same governance.

Analytical tables are in place. Applications and agents also produce and read operational data, record by record, which is a different kind of workload.

Challenges
  • That data usually lives in a separate database with its own copy, and it is not governed there.
  • Feeding analytics from it takes replication pipelines and a second system to maintain.
  • The copies lag behind the source.

Lakebase keeps that data next to the analytics, under the same rules.

  • It is a serverless Postgres database inside the platform, for the state of applications and agents.
  • Synced tables bring lakehouse data into Lakebase, and Lakehouse Sync writes Lakebase tables back to the lakehouse.
  • Lakehouse//RT answers SQL queries in under a second directly on lakehouse tables, so dashboards and applications read them without a separate serving copy.
  • LTAP is the architecture these capabilities deliver: one dataset, written in Lakebase and read in Lakehouse//RT, with no replication pipeline between them.

1.4 Table Maintenance

Tables stay fast on their own, with no maintenance jobs to schedule or own.

Tables written all day, by pipelines and by applications, fill with small files and old versions, and query times suffer.

  • Predictive Optimization is enabled by default on Unity Catalog managed tables.
  • It decides when to compact files, remove old versions and cluster the data, based on how it is queried.
  • It runs on serverless compute, and each decision is recorded for audit.

For a decision-maker, this layer is where the risk of AI on company data is managed.

Unity Catalog

2.1 Catalog & Access

One set of permissions and one lineage graph cover every asset on the platform.

Registration comes first: an asset the catalog does not know cannot be governed.

  • The catalog organizes every asset, and Discover lets users find them.
  • Lineage follows the data across the platform, and external lineage extends it to systems outside Databricks.
  • Access is granted by role or by attribute.
  • Users can request access to an asset.
  • Other engines access the same tables through catalog commits and the Unity REST API.
  • Secrets are stored and governed in the catalog.

2.2 Policy & Classification

A rule written once follows sensitive data wherever it is copied.

Permissions by role or attribute say who may read a table. They do not say what the table holds, and a rule about personal data needs to know that.

  • Data classification tags sensitive data such as PII.
  • Governed tags carry those labels, and tag propagation applies them to the data derived from a tagged table.
  • The tags feed row- and column-level access policies.
  • Governance Hub shows the state of governance in one dashboard.

2.3 Observability

Quality problems in tables are detected before users notice them.

Access and policies are set. The data they cover also has to stay fresh and complete, or every model and answer downstream inherits the fault.

Challenges
  • Data freshness is invisible and nobody is notified, so a stale table can go unnoticed.
  • Repairing it is manual and risky.

Data Quality Monitoring puts quality checks where access is controlled.

  • Profiles track metrics over time and detect drift in tables and in predictions.
  • Anomaly detection flags stale or broken tables and can trigger a repair job.
  • Health indicators show the quality and freshness of each table in the catalog.
  • Alerts go out by email, Slack or webhook.

3.1 Workspace

Data scientists work on governed tables with a coding assistant in the same place.

Work starts where the data is.

  • Data scientists work in notebooks that run Python, SQL, R and Scala directly on the governed tables.

  • It writes and explains code from plain-language requests, in a pane next to the notebook or on a full page.
  • A command-line version brings it into the terminal and into CI pipelines.
  • Genie Code also runs scheduled tasks, including as a task in Lakeflow Jobs.

3.2 Feature Engineering in Unity Catalog

Build features once and reuse them across teams and models.

Exploration ends in features, the inputs a model learns from, and a feature is only worth keeping if the next team can find it and trust it.

Challenges
  • A feature computed one way for training and another way in production gives wrong predictions.
  • Teams duplicate the same features across projects.
  • Nobody sees where each one comes from or who may use it.

Feature Engineering in Unity Catalog ends the duplication with one shared registry.

  • Feature definitions carry the same permissions and lineage as the tables they come from.
  • Teams write features to feature tables, or declare them as Feature Views, which compute them automatically.
  • Stream Feature Views compute them from streaming data.
  • Training sets are built with point-in-time correct joins, and the same definitions feed predictions in production.
  • For real-time use, features are served from an online store on Lakebase.
  • Feature serving returns them over REST, and models look them up automatically at inference time.

3.3 Training Compute

Teams train large models without building or operating clusters.

Training on those features is the first step where compute becomes the constraint: some datasets and models do not fit on one machine.

Challenges
  • Distributed training code is hard to write correctly.
  • GPUs are scarce.
  • Clusters configured by hand are error-prone or sit idle.

Databricks Runtime for Machine Learning and AI Runtime are the two compute options.

  • Databricks Runtime for Machine Learning runs training on classic clusters, with managed libraries such as TorchDistributor, DeepSpeed and Ray.
  • AI Runtime provides GPUs on demand with no cluster to manage, and it scales to zero when the job ends.
  • The AI Runtime SDK spreads training across GPUs, and the AI Runtime CLI submits it from the command line.
  • Fine-tuning of language models runs on the same AI Runtime (see Agent Development).

3.4 MLflow 3

ML lifecycle management

Repeat any experiment, and know which version runs in production.

With compute in hand, a team trains many models and compares them, over months and across people.

Challenges
  • Each team keeps its metrics to itself.
  • Nothing tracks model versions over time.
  • Promotions are manual and error-prone.

MLflow keeps the record.

  • It records every training run with its parameters, metrics, code version and artifacts, so any result can be reproduced and compared.
  • Every model in production is registered in Unity Catalog with its versions, its aliases such as champion and challenger, and its lineage back to the training data.
  • Promoting a new version means moving an alias, and model update triggers or deployment jobs can start the next steps automatically.
  • Experiments, models and prompts live in Unity Catalog with the same permissions as tables.

3.5 Model Serving

ML models

Any registered model answers requests, in real time or in batch, with no serving stack to run.

A registered version is a record. To be useful it has to answer requests.

Challenges
  • Each kind of model needs its own serving system, provisioned by hand, with access control split across them.
  • Idle machines keep costing money.

Model Serving is one serverless service for every model type.

  • Its endpoints run the registered version, for real-time requests and for batch scoring.
  • Custom model endpoints serve models built with scikit-learn, XGBoost, PyTorch or Hugging Face.
  • Endpoints scale with demand, down to zero.
  • Endpoint telemetry monitors the usage of each endpoint.
  • Inference tables keep each request and its response in a Delta table.

Agent Development

4.1 Model Access

No agent is tied to one model or one provider.

An agent starts with a model. Which one, and from which provider, will change over the life of a project, so the choice must stay cheap to revisit.

Challenges
  • Depending on one provider creates lock-in.
  • Models from different providers are tested piece by piece.

Foundation Model APIs serve the hosted models through one API.

  • The hosted models come from providers that include Anthropic, OpenAI, Google and Meta.
  • They are billed per token, with a priority option, or with provisioned throughput.
  • The catalog includes OpenJev, the Databricks judge model.
  • Because applications call the same API for every model, moving to a newer model stays a small change.
  • Models hosted at a provider are registered as external models, with their keys stored centrally.
  • Unity Gateway is the single access layer in front of all of these models.

6.2 Unity Gateway: Policies

  • It works with coding agents such as Claude, Codex or Cursor.
  • Agents are defined in portable YAML, for local or managed execution.
  • Developers can share a live session.
  • The managed version runs code in Databricks Sandbox.
  • The agentic code converter translates SQL written for other warehouses into Databricks SQL.

Vertical Applications

Vertical Applications

9.1 CustomerLake

customer data platform

Campaigns and personalization run on governed customer profiles that stay current.

The first is for customer data, which every business function reads and writes.

Challenges
  • Each system holds its own part of the customer, often duplicated and without lineage.
  • Audiences are built and activated by hand.

CustomerLake covers this work as a ready-made application.

  • It joins transactions, behavior and engagement into one profile per customer, on the lakehouse.
  • AI-assisted identity resolution merges duplicate records.
  • Campaign agents create and activate audiences, and a real-time profile API feeds personalization.

Vertical Applications

9.2 Lakewatch

agentic SIEM

Security logs stay on the lakehouse and agents investigate the alerts.

CustomerLake applies the platform to customer data. The same pattern applies to security data, where volume is the problem.

Challenges
  • Telemetry is split across separate tools.
  • Threat hunting and triage are manual.
  • Detection rules are hard to version and test.

Lakewatch runs security operations on the lakehouse.

  • It keeps security, IT and business logs in one place at object-storage cost, so long retention is affordable.
  • Autonomous agents investigate alerts and help write detection rules, which are versioned and tested like code.
  • Panther, whose acquisition Databricks has announced, brings its detection engine to Lakewatch.

Closing

The result is open tables, one catalog that governs them, models and agents built on both, every call measured and controlled, and business users served in plain language.

Each new layer reuses the catalog, the compute and the serving layer beneath it, so adopting agents does not mean rebuilding the data platform.

The data stays in the organization's own storage, in open formats, and the choice of models stays open.
